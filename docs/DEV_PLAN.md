# 开发计划 v1.3（2026-09-22 定）

> 进度（2026-09-22 晚）：P1 ✅ / P2 ✅ / P3 ✅ / P4 ✅；另完成真实语料深测（7 书 3618 块，结论进 FEATURES §9）。以下"现状盘点"为定稿时快照。

## 现状盘点（全部可复核，数字来自 eval/baseline.json 与实测）

- 链路：上传(PyMuPDF逐页/扫描页rapidocr) → Chroma(bge-small-zh) + jieba BM25 双路 → RRF(k=60,池8) → LLM listwise 重排 top4 → 生成 → 引用核验 → 会话/长期记忆。
- 已达标：G1 REST 契约 26 项（scripts/api_contract_test.py）；G2 SSE；G3 金标 29 条六类 + strict 门禁；G4 OCR；L1-L5 分级全过。
- 基线：rerank hit@1 0.923 / hit@4 0.923 / MRR 0.923；仅 RRF 通道 hit@1 0.846；拒答 1.0；**paraphrase 类 0.6（唯一低于 1.0 的类别）**。
- 实测延迟：单查询 30~50s（LongCat，改写+重排+生成 3 次 LLM 往返）；评估全量 29 题约 13 分钟且依赖外部服务稳定性。

## 已知弱点（本计划要打的靶子）

1. 重排用 LLM listwise：慢、贵、不可离线，且评测被外部 API 可用性绑架。
2. paraphrase 0.6：kb_sample.txt 单大块导致同义问法命中后位次差，分块策略一刀切（固定字符数）。
3. 金标 29 条全是单轮（use_history=false）；查询改写做了，但没有任何多轮指标证明它有用。
4. 质量度量只在检索侧；生成侧只有"引用是否存在"，没有"答案是否忠于资料"的量化。
5. 语料 5 个文档，所有性能结论在 10² 数量级之外没有证据（BM25 全内存遍历、Chroma 单集合）。
6. 无 CI；契约测试与门禁只能靠手跑。

## P1 本地 cross-encoder 重排 ✅（`3033f51`）

- 方案：`bge-reranker-base`（onnxruntime 已有，CPU 可跑）作为新通道，配置 `RERANK_MODE = llm | ce`，默认 ce；LLM 通道保留作对照。
- 验收：`--strict` 全绿（rerank 指标不低于基线）；单查询端到端 < 15s（同题同语料，实测贴数）；`scripts/compare_rerank.py` 输出 llm/ce 两通道每题位次对比。
- 实测：热路径端到端 5.8s（原 30~50s）；重排 hit@1 0.923→0.962、hit@4 1.0；adversarial 0.75 为 ce 跨语言边界（见 FEATURES §9）。

## P2 分块策略实验 ✅（`48562ac`）

- 方案：按标题/空行结构优先切（Markdown/文本），块大小做成可配；预留 small-to-big：检索用小块、喂生成用其父段。
- 验收：金标其余类不掉，paraphrase 类 0.6 → ≥0.8，`--update-baseline` 固化并在提交说明写实验数据；trace 面板里能看到切块边界对命中的影响（拿值班/星尘那两个失败题做前后对照）。
- 实测：structure@300 下 paraphrase hit@1 0.6→1.0，重排 hit@1 0.923→0.962（实验明细 eval/chunk_experiment.json）。

## P3 多轮对话评测 ✅（本次提交）

- 方案：金标新增"对话类"——每题是一段多轮脚本（先陈述背景，再问带指代的追问），期望经改写后命中正确文档；`evaluate_retrieval.py` 支持 session 模式（use_history=true 串跑）。
- 验收：新增 ≥6 组多轮题，拒答类不受扰动的同时 multi_turn 类 hit@4 ≥0.8；给出"关掉改写"的 ablation 数字（预期显著掉分，否则说明改写本身无效，结论如实写）。
- 实测：10 组多轮（8 可答 + 2 会话内拒答），改写开 multi_turn hit@1/hit@4/MRR = 1.0/1.0/1.0、拒答 5/5；改写关 hit@1 0.5、MRR 0.688（hit@4 仍 1.0，裸指代掉位次不掉命中）；改写 10/10 正确消解。金标扩至 39 题，基线随之刷新（重排 0.971/1.0/0.98）。

## P4 生成质量量化（faithfulness）✅（本次提交）

- 方案：抽样 15 题人工+LLM 双评：答案每个句级论断能否在引用资料中找到支撑；产出 `eval/faithfulness.json`；与现有引用核验对照（核验通过率 vs 真实忠实率，验证规则层是否够）。
- 验收：有数字、有分歧样本清单；若规则核验漏检 >10%，针对性补规则（不默认加 LLM 往返）。
- 实测：`scripts/evaluate_faithfulness.py` 抽 13 题（六类全覆盖，含 3 道多轮）拆出 22 条句级论断，LLM 评审 22/22 supported，忠实率 1.0，规则层漏检 0 例（<10%，不补规则）。首轮唯一分歧样本（一句"引用资料编号："被判 not_supported）人工复核为拆句器遗留的标签碎片，修 `CITE_LINE_RE` 后消失。边界：样本仍是 tiny 语料、评审模型与生成模型同源（LongCat 自评），结论强度受限。

## P5 规模与工程加固（量力做，可延期）

- 合成语料压测脚本：生成 500/1000 文档，量上传吞吐、检索 P95、BM25 内存曲线；结论写进 FEATURES「已知边界」（大语料到什么规模开始退化，有图有数据）。
- CI（GitHub Actions）：契约测试 + 无 key 抽取式冒烟（pip 装依赖含 onnx）；不跑 LLM 依赖的评估。
- 结构化访问日志（每题一行 JSON：耗时分解/通道命中），面板可读。

## 明确不做

鉴权/多租户/多 worker；Agent 流式；版面级表格解析；自动调参/自训练。

## 执行约定（沿用 v1.2 已验证的方式）

每阶段独立提交；验收看真实产出（答案原文、位次表、耗时数字），不看状态码；动检索链路必跑 `--strict`；增删语料必同步金标并 `--update-baseline` 写理由。
